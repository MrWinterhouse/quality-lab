Case study 04 · Rules and differential testing · back to all

A family of four is told it qualifies. It doesn’t.

Biweekly pay is annualized over 24 periods instead of 26, and the Alaska and Hawaii poverty multipliers are declared, then multiplied by one. Two silent wrong answers in opposite directions, found by comparing the API to an independently written oracle.

Defects
DEFECT-01, DEFECT-02, DEFECT-13
Area
Policy rules, arithmetic, differential testing
Severity
Critical — silent wrong eligibility
Evidence
tests/probes/policy.probes.test.ts, differential.probes.test.ts

The system

Screening takes a household — state, size, members, each member’s income and frequency, immigration status, pregnancy, whether income is complete — and returns a status per program: Medicaid, SNAP, WIC, CHIP. Medicaid’s limit is 138% of the federal poverty level in expansion states and 100% elsewhere. SNAP uses 130%, WIC 185% with a categorical requirement, CHIP 200% with a child under 19.

The interesting property of this class of code is that it is pure arithmetic with a policy sentence on top. Nothing crashes. A wrong answer looks exactly like a right one — a status field and a percentage — and the person on the other side acts on it.

What I tested

Three layers, because unit tests written by the same person who wrote the code tend to inherit the same misunderstanding:

  1. Table-driven boundaries. For each program, just below, exactly at, and just above the limit, for each income frequency.
  2. An independent oracle. python-oracle/rules.py, standard library only, written from the specification rather than ported from the JavaScript. The probe pipes household JSON in and compares the program statuses that come back.
  3. Invariants. More income never increases eligibility; adding a member never decreases the income limit; the same household screened twice returns the same answer.

The oracle is the part that found these. A unit test asserting the code’s own arithmetic agrees with itself; a second implementation written from the spec does not.

What I found

1. Biweekly is not semimonthly

// product/server/lib/policy.mjs
case 'weekly':      return amount * 52;
case 'biweekly':    return amount * 24;   // ← 26 pay periods exist
case 'semimonthly': return amount * 24;   // correct

Two labels that look interchangeable are not. Semimonthly is 24 paycheques a year — twice a month. Biweekly is every two weeks, which is 26. Fold them together and you understate annual income by 7.7%, which is exactly enough to move someone across a threshold.

A family of four in California, one earner paid $1,800 every two weeks:

One wrong multiplier, one flipped status, no error anywhere. The household is told it likely qualifies for Medicaid when it is $2,450 of income over the line.

2. A multiplier that multiplies by one

export function fplAnnual(householdSize, state) {
  const base = /* table lookup */;
  const stateMultiplier = 1;          // ← computed, then unused
  return Math.round(base * stateMultiplier);
}

Alaska and Hawaii have their own, higher poverty guidelines. The oracle encodes them as 1.25 and 1.70; the product encodes 1 for every state in the country. The dead variable is the tell — someone intended to look the value up and shipped the default.

Note the direction. The biweekly defect overstates eligibility, which creates improper enrollment and audit exposure. The Alaska defect understates it, which denies coverage to someone who qualifies. Both are silent, both are one line, and neither would be caught by a test that only asserts “a response came back”.

3. The differential probe

The probe spawns Python, feeds it the same households the API receives, and compares four statuses per case: 

const expected = runOracle(python, CASES);        // python-oracle/rules.py
const actual = [];
for (const testCase of CASES) {
  const screening = await createScreening(app, testCase);
  actual.push({ medicaid: ..., snap: ..., wic: ..., chip: ... });
}
assert.deepEqual(actual, expected.map(...), 'the API and the independent oracle disagree');

It fails on the biweekly case and the Alaska case, and passes on a plain monthly California household. That third case matters: a differential test that fails everywhere tells you the harness is broken, not the product. One green case keeps the oracle honest.

Why it matters

  • It is a determination, not a display. The status feeds an application, a caseworker queue and a letter. A false eligible can become an improper payment; a false ineligible can become a denied benefit with an appeal deadline attached.
  • It is silent and plausible. The response contains a percentage and a reason code. Nothing about “134.4% of FPL” looks wrong unless you recompute it.
  • It is systematic. The same multiplier is applied to every biweekly household in the system, and every household in two states. This is not an edge case; it is a bias.
  • It survives ordinary testing. All 44 baseline checks pass, because the baseline checks assert the arithmetic the code actually performs.

The fix

Make the frequencies data instead of a switch, so the 24/26 distinction is a value someone can review, and test it at the boundary for every entry: 

const PAY_PERIODS = { hourly: null, weekly: 52, biweekly: 26,
                      semimonthly: 24, monthly: 12, annual: 1 };

For the guidelines, replace the constant with a versioned table keyed by state and effective date, and delete the dead multiplier. Then make the differential suite blocking in CI with generated households seeded around every threshold — not three hand-picked cases.

One honest caveat on the fix itself: the real guidelines publish separate Alaska and Hawaii tables, not a multiplier. The lab uses 1.25 and 1.70 as a simplification, and the fix has to bring the published table with its effective dates, not a tidier constant. Policy arithmetic that ignores effective dates is the same class of bug waiting for January.

Acceptance criteria

  • Every income frequency has a table-driven test at the limit, ±$1.
  • Biweekly and semimonthly produce different annual figures for the same amount.
  • Alaska and Hawaii use their own guideline table, versioned by effective date.
  • The differential suite is blocking and runs on generated households.
  • A rule change is a fixture diff a reviewer can read, not a code edit they must trust.

What this does not prove

The oracle is independent in implementation, not in policy. It was written from the same simplified specification, so it cannot tell me whether 138% is the right threshold or whether this state should be an expansion state — only whether the API computes what the spec says. Both implementations also share my assumptions about which programs exist. Independence buys arithmetic agreement, not policy truth, and the fixture tables are not authoritative for any real program.

A unit test that recomputes the implementation proves the implementation is consistent. Only a second implementation, written from the sentence, can prove it is correct.
