Case study 02 · Async integration · back to all

One application, two income verifications

The vendor processes the request, then times out. The retry loop asks again with a new idempotency key, so the vendor records a second verification — and the application timeline reports a single, clean success.

Defect
DEFECT-07
Area
Retries, idempotency, event truthfulness
Severity
High — silent duplication
Evidence
tests/probes/async.probes.test.ts

The system

Submitting an application kicks off an asynchronous income check. A worker calls a simulated third-party vendor with the application id, a hash of the household data, and an idempotency key. The vendor either returns a verification, returns a duplicate of one it already has, or fails. The application records the result as an event on its timeline.

The vendor simulator is deliberately crueller than a happy-path stub. It can fail before doing anything, fail always, or — the case that matters here — complete the work and then fail, which is what a real timeout looks like from the caller’s side.

What I tested

Idempotency is only interesting under failure, so I ignored the success path and drove the three failure modes through the public API, asserting on the vendor’s state rather than on the HTTP response:

  • Fail after recording — the vendor stores the verification, then returns 504.
  • Always down — every attempt fails; the workflow must terminate, not spin.
  • Fail before recording — a retry should legitimately create the first record.

The assertion that matters is not “it eventually succeeded”. It is how many verification records exist for one application after the dust settles.

What I found

The retry loop builds its key inside the loop, from the attempt counter:

for (let attempt = 1; attempt <= 3; attempt += 1) {
  try {
    const idempotencyKey = `${application.id}:${attempt}`;   // ← changes per attempt
    const result = await vendor.verify({
      applicationId: application.id,
      householdHash: application.householdHash,
      idempotencyKey,
    });
    application.vendor = { status: 'verified', verificationId: result.verificationId };
    store.addEvent(application, 'vendor.verified', { verificationId: result.verificationId });
    return;
  } catch (error) {
    if (attempt === 3) { /* mark failed */ return; }
    await delay(10);
  }
}

An idempotency key is a promise that “this is the same logical request as before”. Deriving it from the attempt number promises the opposite: every retry declares itself a new operation. The vendor has no way to deduplicate, because it was never told these calls were related. 

curl -s -X POST http://127.0.0.1:4310/internal/vendor/config \
  -H 'Content-Type: application/json' -d '{"failAfterRecord":1}'
# then create a screening, submit an application, wait for verification

curl -s http://127.0.0.1:4310/internal/vendor/state
# { "attempts": 2,
#   "verifications": [
#     { "verificationId":"vrf_00001", "idempotencyKey":"app_00001:1" },
#     { "verificationId":"vrf_00002", "idempotencyKey":"app_00001:2" } ] }
# expected: one record

Two records for one application, produced by one user action. The probe asserts records.length === 1 and attempts >= 2, so a “fix” that simply stops retrying fails the second assertion and a fix that reuses the key passes both.

The part that makes it worse

The timeline shows one event: 

{ "type": "vendor.verified",
  "data": { "verificationId": "vrf_00002", "duplicate": false } }

There is no trace of vrf_00001 — no failure event for the timeout, no acknowledgement that two records exist. An auditor reading the application sees a single clean verification. The duplicate lives only in the vendor’s system, where nobody in this product is looking.

Why it matters

In the lab the consequence is an extra row. In a benefits system the verification record is what an approval hangs on, and duplication compounds:

  • Duplicate approvals. Two verification records for one household can drive two approvals, two payments, and a reconciliation break that surfaces months later.
  • An untrue audit trail. The timeline is the artifact a caseworker and an auditor rely on. It reports one success and omits the failure that caused the retry, which is the single most important fact about the transaction.
  • Vendor cost and rate limits. Every timeout is billed and counted; retrying under a new key turns a transient failure into a duplicate charge.

It is also the failure mode most likely to be missed, because it needs the vendor to fail after doing the work. A test suite that only simulates “vendor is down” never reaches it.

The fix

Key the logical operation, not the attempt. The verification is identified by the application and the household data it validates; if either changes, it is a different operation and deserves a different key. 

const idempotencyKey = `verify:${application.id}:${application.householdHash}`;
for (let attempt = 1; attempt <= 3; attempt += 1) {
  try {
    const result = await vendor.verify({ applicationId: application.id,
                                         householdHash: application.householdHash,
                                         idempotencyKey });
    ...
  } catch (error) {
    // record the failed attempt on the timeline, not just the final outcome
  }
}

Two smaller changes belong with it. Record each failed attempt as an event, so the timeline explains the retry. And replace the fixed 10 ms delay with bounded exponential backoff plus jitter — three attempts 10 ms apart is a retry storm against a vendor that is already struggling, not resilience.

Acceptance criteria

  • A timeout after processing produces exactly one vendor record.
  • The retry reuses the same key and the vendor returns the existing record as a duplicate.
  • An always-down vendor terminates in a failed state after a bounded number of attempts.
  • The timeline contains a failed attempt and one success, not one success alone.
  • The test asserts vendor state and timeline, not just the HTTP response.

What this does not prove

The simulator is cooperative: it records before failing on request. A real vendor may time out after its own internal commit, return a partial payload, or accept the duplicate with a different id. The probe proves the caller now sends a stable key and handles the duplicate it gets back. It does not prove a specific vendor honours it — that needs a contract test against the vendor’s sandbox and an alert on duplicate rate in production.

Adjacent defect in the same area, found while testing this one: the vendor webhook verifies the HMAC but never checks the timestamp, so a captured callback can be replayed (DEFECT-08). Same lesson, different door.

Retries are where a system’s real contract shows up. If the retry cannot say “this is the same request”, the integration has no idempotency — only an intention.
